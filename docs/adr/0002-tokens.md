# ADR 0002: API トークンは opaque Bearer + SHA-256 ハッシュ + ロール部分集合スコープ

- 日付: 2026-10-25
- 状態: 採用

## 背景

CLI と自動化が sys4sys API を安全に操作するには、ブラウザのセッション Cookie だけでなく、機械向けの API トークンが必要になる。一方で、トークンが長い有効期間と広すぎる権限を持つと、漏えい時の影響範囲が大きくなる。既存の Web API は Argon2id + DB セッション認証であり、ロールは `admin` / `operator` / `viewer` である。

CLI は API だけを介して操作する必要がある。SQLite を直接触る、または監査を迂回する運用は避けたい。

## 決定

**opaque Bearer API トークン**を採用する。

- 形式: `s4s_<base64url(32 bytes)>`
- ヘッダー: `Authorization: Bearer <token>`
- DB 保存: 平文全文は保存せず、SHA-256 ハッシュのみ保存する
- 表示用: 先頭 8 文字の `prefix` を保存し、一覧・詳細・監査ログでは prefix だけを使う
- 発行レスポンス: `token` は作成時に一度だけ返す。以後は復元できない
- 期限: 既定 90 日、最大 365 日
- 失効: `revokedAt` を立てると即時無効。物理削除はしない
- ロール連携: 発行時点のユーザーの `role` と `isActive` を検証し、トークンのスコープはロール上限の部分集合でなければならない
- トークン認証での昇格防止:
  - `tokens:manage` を持たないトークンは新しいトークンを作成できない
  - `tokens:manage` を持つトークンでも、発行元スコープの部分集合で作成できる
- 権限検査:
  - 未認証は 401
  - 認証済みだがスコープ不足は 403 とし、Problem Details に `requiredScope` を返す
- 監査: `token.create` / `token.revoke` を記録する。トークン全文、ハッシュ、`tokenHash` は記録しない

CLI の環境変数は `SYS4SYS_TOKEN` と `SYS4SYS_TOKEN_FILE` を優先する。`--token` はシェル履歴・プロセス一覧に残る可能性があるため採用しない。

## 理由

- 平文保存を避けられる
- prefix と scope だけで運用管理でき、漏えい時は該当 token id を revoke できる
- ロール上限と部分集合検査で、トークン権限の昇格を抑制できる
- 監査ログに秘密値を載せない
- CLI・CI からは環境変数またはファイル経由で安全に注入できる

## 代替案

- **JWT**: ステートレスだが、即失効・スコープ監査・DB 連携が複雑になる。sys4sys は即失効と監査を優先するため却下
- **セッション Cookie の CLI 保存**: 人間向けブラウザ認証と機械向け認証を混在させることになり、トークン管理・部分スコープが作りにくい。CLI の永続認証用に credential store は残すが、API 呼び出しの第一選択は Bearer とする
- **API key を平文保存**: 実装は簡単だが、DB 漏えい時にトークン全文が流出するため却下

## 運用上の注意

- `SYS4SYS_TOKEN` を会話、Issue、PR、ログ、コミットに書かない
- CI では OIDC / Secrets Manager / ワークロード アイデンティティなど、可能な限り短い期間で使える管理機構を使う
- 長期運用が必要な場合も、用途別に最小スコープで発行する
- `tokens:manage` は admin だけの強い権限。他ユーザーのトークン管理にだけ使う
- トークン全文が一度だけレスポンスに含まれるため、発行直後に secret store に保存し、CLI 出力は再表示しない
